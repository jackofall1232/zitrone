## Findings

### FINDING 1 — MEDIUM: the stale-completion fix covers only successes; a stale FAILED completion is still re-applied unconditionally, racing the boot authority

`apps/android/app/src/main/java/com/zitrone/app/MainActivity.kt:830-881` (burn observer) vs `:755-804` (boot re-derive).

`BurnCompletion` is process-lifetime and never cleared — the premise of 5ef5f77. The new `IGNORE_STALE` predicate is `burnReportedSuccess && vaultImagePresent` (`ZitroneApp.kt:1502`). By construction it cannot see the failure-side stale case. Concretely:

1. Burn fails in a way that leaves the vault unlockable (e.g. a temp-unlink failure → `DestroyFailed`; `burned=false`, `BurnCompletion(1, obliterated=false)` published, `MainActivity.kt:1075`). LOCKED arm applies — correct.
2. User unlocks with the correct passphrase (vault survived), then deletes the account. D2c's destroy succeeds: files gone, both markers retired, `route = Route.Onboarding` (`MainActivity.kt:1392-1401`).
3. Rotation. The composition re-seeds `route = Splash`, but `burnCompletion` still holds `BurnCompletion(1, false)`. The observer re-fires, reads `{confirmed=false, obliterationComplete=true, hasVault=false}`, and `postBurnRoute(false, false, true, false)` falls to the `else → LOCKED` arm — which it applies **with no route guard and no staleness check**: `vaultExists = true`, `lockError = UNIFORM_FAILURE`, `route = Route.Locked` (`MainActivity.kt:873-879`) — over a device with **no vault at all**. Every passphrase entry then maps `MissingImage → Rejected` (`ZitroneApp.kt:540-552`); there is no path to onboarding; soft-brick until process death, with a wrong-passphrase error the user never earned — the exact prior-use-tell class 5ef5f77 was written to eliminate.

Worse, it's nondeterministic: the boot re-derive effect computes `ONBOARDING` for the same disk state (`bootRoute(false, false, hold=false, provenAbsent=true)`) and applies it only `if (route == Route.Locked)` (`MainActivity.kt:800`). Both effects suspend on `Dispatchers.IO` after already-true gates, so which writer lands last is a race. If the observer wins: bricked lock screen. If the re-derive wins: correct onboarding.

A second shape needs no account deletion: a burn whose unlinks landed but whose `dirSync` was `NOT_DURABLE` (`obliterateLocked` throws at `VaultImageStore.kt:1179` with the files actually gone). The observer says LOCKED (correct under the unit's own non-durability doctrine — `residueSweepHold` exists precisely for "a stat says absent, a journal replay disagrees"), while the boot re-derive says ONBOARDING from `vaultProvenAbsent()=true` — **the burn's non-durability is carried nowhere**; `residueSweepHold` only covers the sweep. Same race, and here one of the two authorities violates the fail-closed verdict the dispatcher published. This is the unit's named pattern one more time: an authoritative result exists (`BurnCompletion.obliterated=false`), and a second consumer routes from a weaker signal (fresh stats that cannot see durability) — forms (c) SECOND AUTHORITY and (d) INCOMPLETE INPUT SET.

**Why it matters.** The onBurn comment at `MainActivity.kt:1077-1082` declares "SINGLE ROUTING AUTHORITY"; post-burn that is not actually true on a recreated composition. Note the new tests lock the pure function in: `proven absence without reported success is still a lock screen` (`PostBurnRouteTest.kt:85`) asserts LOCKED for exactly the shape-1 input tuple — the function does what it's told; the defect is at the **consumption site**, which no test reaches (no Compose infra).

**Calibration.** The whole path is unreachable in production today (slot 0 unarmed), and by the maintainer's own round-5 rubric ("LOW rates the CODE; the property it degrades is the whole deliverable") this is the same class as the finding 5ef5f77 fixed — with a worse worst case (brick + nondeterminism vs. a cosmetic error). I rate MEDIUM; LOW is defensible under that rubric, but it should be fixed or explicitly ratified before Unit S arms slot 0, not carried silently.

**Concrete fix.** The account-delete completion paths (`onDeleteAccount`'s confirmed `finally` at `MainActivity.kt:1388`, and `onRetryDestroy` at `:651`) are the only legitimate post-burn image destroyers — have them clear/overwrite `container.burnCompletion` on a confirmed destroy, making any prior completion definitionally stale in both directions. For the non-durable-burn shape, either carry the burn's durability verdict into the same hold the boot authority consumes, or gate the boot re-derive to defer when `burnCompletion.value != null` so the observer is genuinely the single post-burn writer.

### FINDING 2 — LOW: `PostBurnRouteTest.full truth table` asserts an exhaustiveness it no longer has

`apps/android/app/src/test/java/com/zitrone/app/PostBurnRouteTest.kt:128-155`.

5ef5f77 grew `postBurnRoute` to four inputs but left the truth table at 8 rows over three inputs (taking `vaultImagePresent`'s default), still asserting `"the table must cover every combination", 8, expected.size`. That message is now false — 8 of 16. Uncovered combinations include `{confirmed=true, success=false, present=true}` (does the confirmed marker still outbid a failed burn when an image is present? — the D2c/staleness interplay the commit itself is about) and `{confirmed=true, success=true, provenAbsent=true, present=true}`. The sibling suite had **exactly this defect** found in round 4 and fixed by sweeping all 32 combos — `BootRouteTest.kt:209-236` even names the class in its kdoc ("swept only four and took `legacyImage`'s default… while the function had grown a fifth input"). The same commit reintroduced it next door. `onboarding is reachable from exactly one input combination` (`:161-175`) likewise sweeps only the 8-combo subspace (the claim happens to still hold in 16, but the test doesn't prove it).

**Fix.** Extend the table to 16 rows and the reachability sweep to all four inputs, mirroring `BootRouteTest`.

## Verdicts on A–F

**A — verified; the previous lens's conclusion holds, with one refinement.** I enumerated every `route`/`vaultExists` assignment by grep (40 hits) and classified them. The disk-derived decision sites: Splash effect (`:705-753`), boot re-derive (`:755-804`), session-collector null-arm (`:909-956`), burn observer (`:830-881`), onBurn dispatcher (`:1083-1126`). All are ordered after `bootReconciled` (the burn observer isn't gated on it, but a completion can only exist after boot routing produced a lock screen — safe by reachability), all pass the FULL input set (verified 5-arg `bootRoute` ×3, 4-arg `postBurnRoute` ×2), and all boot consumers use the carried `residueSweepHold` rather than re-deriving. The remaining ~15 sites are user-action/session-driven, not disk-derived. One hygiene note (INFO): the session collector's `vaultExists = container.hasVault()` (`:921`) omits the `&& !legacy` correction the other two consumers apply — practically unreachable (a legacy image cannot produce a live session, as the comment says). The refinement: "no further site exists" is true, but the burn observer's *unconditional application* is Finding 1.

**B — correct as far as it goes; incomplete one direction.** `IGNORE_STALE`-first is sound: a FAILED burn can never match it (`burnReportedSuccess=false`), and it cannot mask a confirmed-delete state — when it preempts `DELETE_INCOMPLETE`, that state is still reached via Splash/boot re-derive/session collector, all of which put `serverDeleteConfirmed` first; "applying nothing is always safe" holds because other writers own that state. `burnReportedSuccess && vaultImagePresent` is a correct staleness predicate for successes (in-process, an image can only reappear via a deliberate create after a proven-complete burn). It is not *complete*: the failure-side stale case above. The claim "a FAILED burn is untouched, which keeps the fail-closed LOCKED arm intact" is true of the function and false of the system.

**C — verified, clean.** `bootRoute` precedence (confirmed → legacy → present → hold → provenAbsent → LOCKED) is right in both directions; `legacy+hold` is unreachable (a present bin fails the sweep's gate 1, so no hold can coexist with a legacy image). `runBootReconcile` (`ZitroneApp.kt:1345-1387`): once-only CAS ✓, publication in `finally` on every exit ✓, fail-closed default (`SWEPT_NOT_DURABLE` → hold) ✓, cancellation cannot strand the claim ✓ (and all four are test-proven in `BootReconcileOwnerTest`, which drives real waiters), dispatcher injection is default-`Dispatchers.IO` in production ✓. Production ordering `hold`-then-`done` inside `publish` is fine for `.value` readers.

**D — ratification premises verified in source; table complete.** `destroy()` writes `vault.delete-confirmed` required-durable **before** any unlink (`VaultImageStore.kt:1117`, `:1086-1094`; throws with files untouched — test-proven with a NOT_DURABLE sync). `create()` clears both markers durably (conservative tristate check `:509-514`, `clearBothMarkersDurably` requires re-stat + DURABLE fsync `:1071-1083`) **before** the DEK rename at `:543` — it *clears*, matching the round-2 correction. `obliterateLocked` retires markers strictly after unlinks are verified and fsynced (`:1168-1199`), keys-first. I hunted the missing row across `{bin, dek, tmps, intent, confirmed}`: intent+confirmed together → row 7; legacy image with residue → row 4 (bin present); indeterminate confirmed → row 8; `{no bin, no residue, intent}` is not a sweep state and is owned by `reconcileOrphanedBurnMarkers` (run after the sweep for exactly the 6b reason). The intent-gate removal stands on true premises.

**E — verified.** destroy() equivalence under keys-first holds (the durable confirmed marker bridges any crash point). The four boot healers (sweep → completeInterruptedBurn → reconcileOrphanedBurnMarkers → DeleteIncomplete/destroy, plus the post-unlock intent reconcile) partition the state space with no overlap, contradiction, or ownerless state I could construct. WRITER/READER invariants hold for markers (tristate on destructive reads, correct bias per reader type) and in-flight verdicts (`obliterated` carried, never re-derived; sweep verdict carried into the hold). Reachability: slot 0 is random filler (`VaultSlots.kt:139-142`), `attemptUnlockOrAdd` has exactly one production caller, `Burn` is dispatched only at `MainActivity.kt:1145`, and the unreachability is test-proven. A partial burn cannot present as success; the "worse than not burning" residual (app-local state cleared while the image survives) is deliberate, ordered, and disclosed in both code and SECURITY_MODEL.md. The burn-arm timing/fail-closed behavior in `attemptUnlockOrAdd` (`:721-732`) is correct, including corrupt-burn-payload parity.

## Merge verdict

**Not quite.** The destructive core (D, E) is solid — the best-verified part of the unit, and the round-5 `IGNORE_STALE` fix itself is correct for what it targets. But Finding 1 is the same defect class the maintainer chose to fix rather than carry at the round cap, with a worse worst case, and Finding 2 is a ten-minute test repair. Both are cheap; neither requires redesign. Fix or explicitly ratify Finding 1 and extend the truth table, then this is ready. Nothing here touches the armed-only-in-production invariant: slot 0 stays unarmed and unreachable, test-proven.
