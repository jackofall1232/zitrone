You are auditing a VENDORED semgrep ruleset used as a CI security gate (SAST). The gate runs:
  semgrep scan --config .semgrep --error --strict

CRITICAL FRAMING: --strict catches rules that FAIL TO PARSE. It CANNOT catch a rule that parses
fine but is SEMANTICALLY WRONG — such a rule matches nothing, the gate stays green, and nobody
ever finds out. That is a SILENTLY DEAD RULE and it is the failure class I am hunting.

A known example already confirmed in this ruleset: two rules use the character class [a-zA-Z0-10].
In regex, 0-10 parses as the range 0-1 followed by a literal 0, so it matches ONLY digits 0 and 1,
not 2-9. (In those two rules it sits in a sanitizer/CLEAN node, so its effect is false POSITIVES,
not a miss — direction matters, so always state the DIRECTION of any defect you find.)

TASK: audit EVERY rule below for semantic defects that --strict would not catch. For each defect:
  - rule id + file
  - the exact defect
  - DIRECTION: does it cause FALSE NEGATIVES (misses real issues / dead rule) or FALSE POSITIVES
    (flags safe code)? This is the single most important field.
  - a concrete code/workflow snippet that demonstrates it
  - severity for a gate whose job is catching supply-chain + injection issues

Specifically look for: character-class/range errors; missing ellipsis making patterns too literal;
overly narrow paths: include scoping; language constructs the pattern misses (e.g. Go's 'any'
alias vs interface{}, which one rule here already misses); metavariable-regex anchoring mistakes;
patterns that can never match due to structural nesting; taint sources/sinks that don't connect.

Be precise and skeptical. Do NOT invent defects — if a rule is correct, do not list it.
Rank findings by severity. Keep it dense.

      references:
        - https://docs.github.com/en/actions/security-guides/security-hardening-for-github-actions#understanding-the-risk-of-script-injections
    # Semgrep's generic `...` ellipsis matches at most `generic_ellipsis_max_span` newlines (default 10),
    # so a `${{ … }}` expression split across many blank lines inside a `run: |` block (GitHub ignores the
    # whitespace) could evade the `${{ ... }}` pattern below. Raise the span to a bound no reviewable
    # workflow could plausibly exceed — a single interpolation spanning 10 000 lines of one run scalar is
    # absurd and would be obvious in review — so line-split obfuscation cannot hide the injection.
    options:
      generic_ellipsis_max_span: 10000
    patterns:
      - pattern-inside: "steps: [...]"
      - pattern-inside: |
          - run: ...
            ...
      - pattern: "run: $SHELL"
      - metavariable-pattern:
          language: generic
          metavariable: $SHELL
          patterns:
            - pattern: ${{ ... }}
