## Q1 — Burn-wipe scope: **LOCAL-ONLY. Unanimous.**
Burn destroys local recoverable crypto only — whole vault image (`vault.bin`), DEK envelope (`vault.dek`), slot 0, biometric wraps/Keystore aliases, live RAM keys, cached plaintext, notifications, app-held auth. It does **not** delete relay accounts.

Grounds (all three agree):
- **Offline guarantee** — duress is often network-denied (seized, faraday, dead SIM). A burn that needs a relay round-trip fails exactly when needed. The one thing burn must do reliably is 100% on-device.
- **Correlation tell** — a relay delete emits a server event time-correlated with the wipe; an adversary joining relay logs to the seized device can *prove* "this device burned at T." The opposite of deniability.
- **D2c collision** — relay deletion partly duplicates the hardened account-delete machine (see Q2).
- **Codex-only structural point:** slot 0 doesn't unlock the independently-encrypted vault payloads, so burn **cannot reliably reach every vault's relay credentials** anyway; adding a cross-vault deletion index/master credential to enable it would create linkage and weaken compartmentalization — a second reason not to.

**Trades away:** relay accounts, public keys, queued ciphertext, and account-creation records survive server-side until independently deleted or aged out; contacts may keep sending to now-unrecoverable identities. Honest claim: *"this device can no longer recover the accounts,"* **not** *"the relay has no record they existed."* Any "best-effort remote shred after local wipe" must be decoupled and opt-in, never part of the definition of burn success.

## Q2 — Burn ↔ D2c state machine: **Reuse the destruction PRIMITIVE, NOT the D2c marker machine. Unanimous — and now source-forced.**

Share the shovel, not the house. Burn needs `destroy()`'s physical core (whole-image unlink + verify-unlink + dir-fsync + RAM-DEK wipe + biometric teardown). Burn must NOT become a new writer to the two-marker protocol (`vault.delete-intent` / `vault.delete-confirmed`) that took review rounds 13–16 to stabilize.

**⚠ SOURCE-VERIFIED (the key finding of this round).** `destroy()` at `VaultImageStore.kt:1056` calls `writeDurableMarker(serverDeletedFile)` — it **writes `vault.delete-confirmed` BEFORE the unlinks**, and it is REQUIRED-DURABLE: if that marker can't be created+fsynced, `destroy()` **throws `DestroyFailed` with the vault files untouched**. So calling `destroy()` unchanged from burn is broken on **three** counts:
1. It asserts a **false fact** — writes "server account confirmed gone" when no server delete occurred.
2. A crash mid-burn restarts into `Route.DeleteIncomplete` ("finish deleting your account") — a **discoverable, non-fresh-install** state that defeats Q4 *and* could later provoke a real network deletion on reconcile.
3. Its **marker-write-first-or-abort** ordering means a burn could **throw before destroying anything** if the marker fsync fails — fail-OPEN, the exact opposite of what a duress wipe must guarantee.

**Therefore:** decomposition is **mandatory, not optional.** Extract (or parameterize) the marker-free physical/cryptographic obliteration path — idempotent, no D2c transition — and have burn call *that*. Burn must also **not** clear genuine pre-existing D2c markers itself; whole-image destruction retires all local state together. Burn still deserves D2c-level review of its own crash/reseal/restart behavior (it's a second terminal-lifecycle writer), just against burn's own fail-closed semantics, not D2c's.

## Q3 — IMAGE_VERSION: **No format change. No version bump. Unanimous, source-confirmed.**
Verified this session and by both repo-reading advisors:
- `IMAGE_VERSION = 3`; v3 byte layout is explicitly "unchanged from v2 — only the placement convention changed" (`VaultImage.kt:25`).
- Slot 0 is already a full slot; fresh onboarding leaves it CSPRNG filler, "indistinguishable from any other slot" (`VaultSlots.kt:23,127`).
- "Armed simply means a passphrase can match slot 0, exactly what tryPassphrase already tests" (`VaultSlots.kt:27`).
- `attemptUnlockOrAdd` already returns `UnlockOrAdd.Burn` on a slot-0 match without writing/wiping (`VaultImageStore.kt:618`).

Arming = seal a real derived credential into slot 0's existing salt+wrapped-key region (payload can stay filler/empty-genesis, sized identically for parity) instead of random filler, then persist the whole image under the existing DEK envelope with the normal atomic image-write discipline. **No new header field, flag, or arm-state bit** (that would violate "no discoverable armed/unarmed artifact"). Caveat (not a format change): single-snapshot indistinguishable only — a before/after forensic/backup snapshot reveals slot 0 changed (see Q5).

## Q4 — Post-burn appearance: **App-local first-run onboarding, claimed honestly. Unanimous.**
After successful local destruction, `hasVault()==false` → the normal `Route.Onboarding` path — same as account-delete success and as a fresh install *of this package on this data dir*. No special "wiped"/error/burn-complete/DeleteIncomplete screen (those are tells). A wipe that *fails* must not look like success (keep `destroy()`'s verify-unlink discipline).

**Achievable claim:** "Zitrone removed the recoverable app-controlled local vault and returned its UI to onboarding."
**NOT achievable — must not be claimed (deliver-then-claim):** "indistinguishable from a fresh/never-used install." Outside app control and surviving a burn: package firstInstall/lastUpdate time + version history, data-dir inode age / ART-odex caches, **cloud/Auto-Backup blobs (can *resurrect* pre-burn state — verify vault is backup-excluded)**, UsageStats/battery/network history, notification history, media/Downloads/screenshots the app wrote, AccountManager entries, keystore metadata, and NAND wear-levelled remnants (unlink ≠ media sanitization; the defensible property is **cryptographic erasure via DEK destruction**, not secure physical overwrite).

## Q5 — Concern union (deduplicated across all three advisors)

**Raised by ≥2 advisors (highest confidence):**
1. **The disappearing settings entry is an armed-state ORACLE — and may be self-contradictory with byte-identity.** "Pucker Burn Password Setup" present⇒unarmed, absent⇒armed. Slot-0 byte-parity hides armed/unarmed in the *image*, but an examiner who knows the APK's settings catalog reads arm-state off the *UI*. **Moonshot's sharper point:** to *make* the entry disappear the app must read an armed-flag at render time — but by design it *cannot* cheaply know slot 0 is armed without running the KDF sweep (that's the whole point of byte-identity). So "disappears once set" seemingly forces a **separate persistent armed-flag** (SharedPreferences/DB/header) — which is itself the discoverable artifact the principle forbids, *and* gets uploaded by Auto-Backup, *and* differs across armed/unarmed devices. **Recommended resolution (Moonshot): the entry NEVER disappears** — armed and unarmed installs present a byte-identical settings screen; the permanent "Pucker Burn Password Setup" item above "Delete Account" is itself the deniability-preserving state. **Flag the locked UX decision as flawed**; if it stands, the flag's storage location must be chosen and justified as an accepted leak (no leak-free location appears to exist). *(all four)*
2. **`destroy()` marker coupling** — the false-`delete-confirmed` / DeleteIncomplete / fail-open-abort footgun. Source-verified above; belongs in both Q2 and Q5. *(Codex, Grok; verified this session)*
3. **First-match wipe collision.** `tryPassphrase` records the FIRST matching slot and slot 0 is swept first — so if a burn passphrase ever equals a real vault passphrase, slot 0 wins and **wipes instead of unlocks**. Permanent, unrotatable credential makes accidental collision catastrophic. **Setup must reject any passphrase that matches an existing slot** (full sweep detects this with no stored verifier). *(Claude implicitly via footgun, Codex, Grok)*
4. **Process-death / power-loss mid-burn.** A coercer can kill the app during the expensive all-slot KDF sweep or during destruction. Burn needs fail-CLOSED restart behavior that cannot reopen or reseal surviving state — and cannot borrow D2c's markers to get it. Unlink key material first (crash leaves it *more* destroyed, never recoverable). *(Claude, Codex, Grok)*
5. **Permanent, unchangeable credential is a lifetime hazard.** Untestable (can't verify what you set without triggering it), unrotatable if compromised/forgotten/coerced-to-set/typed-under-stress, no disarm. Increases accidental-wipe rate and may deter arming — which keeps the settings tell (#1) present longer. Warning acknowledgment is UI-only, changes no storage. *(Claude, Codex, Grok)*
6. **Lock-screen partial-remanence inventory.** From the lock screen there's no live session, so image-unlink alone may leave vault-scoped EncryptedSharedPreferences, auth tokens, roster-repair blobs, boot diagnostics, notification channels, WorkManager jobs, WebView/cookie caches, logcat-backed logs. **Partial wipe is worse than honest failure** — onboarding UI over residual prefs looks "used," and any residue a fresh install wouldn't have is a tell. Burn must enumerate and clear these, and land byte-for-byte the same state as fresh-install / account-delete onboarding. *(Claude, Grok)*
7. **Multi-snapshot arming reveal.** Slot sealing is single-snapshot indistinguishable; a pre/post backup, forensic acquisition, filesystem journal, or cloud snapshot identifies a slot-0-only mutation. Don't generalize the single-snapshot claim. *(Codex, Grok)*
8. **Secure-deletion myth on flash / no NAND sanitization claim.** Defensible property is DEK-destruction cryptographic erasure, bounded by backup and key-copy behavior — never "forensically unrecoverable from the medium." *(Codex, Grok)*

**Raised by one advisor (still valid):**
16. **⚠ WIRING HAZARD — `Burn` outcome vs. general-purpose call site (Moonshot; ship-blocker).** `attemptUnlockOrAdd` returns `UnlockOrAdd.Burn` on a slot-0 match, but it is *also* the natural call site for add-slot duplicate/collision checking and any future change-passphrase flow. If the wipe is wired naively to the `Burn` outcome, then **any** path that tests a candidate passphrase against slots — including onboarding's second-vault add-slot collision check — becomes a wipe trigger (creating a second vault with an unlucky candidate destroys everything: a self-DoS). The wipe MUST be wired **exclusively to the lock-screen unlock dispatch**; every other consumer of the `Burn` outcome must treat it as "collision → reject candidate," never "wipe." *(Moonshot)*
17. **Biometric ↔ slot 0 (Moonshot).** Confirm slot 0 can **never** receive a biometric wrap — a biometric path that bypasses the passphrase sweep would bypass burn *and* create a slot-0-specific Keystore artifact that breaks byte-identity at the keystore level. Confirm PR-3's A-only guard already precludes this, and that the destroy primitive's biometric-key removal covers the burn path (no orphaned keystore entry left as "something was here" residue). *(Moonshot)*
18. **Re-arming after re-onboarding is unspecified (Moonshot).** A burn *consumes* the credential — post-burn slot 0 is filler again, so the feature is silently unarmed. "Permanent/unchangeable" wording may mislead users into thinking protection persists across the burn it just executed. Docs/setup must state: a burn consumes the credential; a fresh vault requires fresh arming. *(Moonshot)*
19. **Post-burn inbound-message / notification surfacing (Moonshot).** A message arriving post-burn could surface a system notification on a "fresh" device — a live contradiction of the deniability story. *(Caveat vs. repo: Android has no push stack — WebSocket-only transport, `MessagingCoordinator` — so FCM-token persistence doesn't apply here; the residual is a post-burn inbound-while-onboarding path, not a push registration. Post-burn startup must ensure no notification channel can display anything.)* *(Moonshot, adjusted to source)*
20. **Boot-time reconciliation pass for interrupted burn (Moonshot).** With keys-first ordering (Q2) and no D2c markers, a power-cut mid-burn (battery pull under duress) can leave `vault.bin` present / `vault.dek` absent (or vice-versa) — a half-state that is maximally "app was wiped"-looking (defeats Q4). Startup should silently *complete* the teardown on any such inconsistency: a read-and-complete check that writes nothing and leaves no marker. One more path to audit, cheap insurance. *(Moonshot; complements #4)*
9. **Forensic-image-first defeats any on-device burn** — a competent adversary images the device *before* compelling unlock, then analyzes the copy. Burn defends "hand me your phone and unlock," NOT "seized + imaged." State the bound. *(Claude)*
10. **Whole-image burn = conspicuously empty phone under direct observation** — nukes ALL vaults; a suddenly-empty device may itself provoke the coercer. The locked "visible onboarding reset" is the *least* deniable post-state; a decoy-unlock model (not in the locked design) would be more deniable. Worth an explicit product decision. *(Claude)*
11. **Backup/restore resurrection** — if Auto-Backup is on, a cloud restore can undo the burn. Verify `allowBackup`/backup-rules exclude vault data; if not, it's a burn-defeating hole. *(Claude; overlaps Q4)*
12. **Wipe timing is wall-clock observable** — KDF parity is uniform through the `Burn` return, but the subsequent MB-scale unlink + Keystore + prefs clear is stopwatch-visible; a coercer timing entry can distinguish burn from wrong-password *after* the uniform crypto phase. Document as accepted residual (same class as create-persist residual), not as timing-hidden. *(Grok)*
13. **Fail-closed stub masks a future behavior change** — today `onBurn` looks like a wrong password (`MainActivity.kt:786`); shipping the real wipe changes lock-screen semantics for that credential class across versions (matters for the examiner-facing "this build wipes" honesty narrative). *(Grok)*
14. **Biometric/coercion interaction** — compelled biometric opens only the bound vault (never burn); a coerced "password" may hit vault A/B, burn, create, or reject. Users may arm burn yet reflexively open the real vault under biometric stress. The training/UX assumption is unstated. *(Grok)*
15. **Setup race vs live sessions / second-vault create / pending delete-intent** — arming rewrites the shared image; needs the same `imageLock` discipline as account-delete, and a rule for setup while a session is live or delete-intent is pending (probably refuse setup). *(Grok)*

## Bottom line for the next unit (when this moves from advisory to spec)
- **Q1/Q3/Q4 are settled** and source-consistent: local-only wipe; no format/version change to arm; honest app-local onboarding claim only.
- **Q2 is settled *and now has a hard implementation constraint*:** you cannot call `destroy()` as-is. Introduce a marker-free `obliterateImage()` primitive (idempotent, fail-closed, key-material-first ordering, no D2c transition) that both `destroy()` (which then adds its confirmed-marker semantics on top) and burn call. Build the WRITER/READER invariant table for burn's crash/restart behavior before coding (per repo DoD).
- **Q5 must produce two decisions the locked design doesn't currently resolve:** (a) the **settings-entry arm oracle** (#1) — the locked "disappears once set" UX appears to violate a standing principle; escalate for a product decision, and (b) the **remanence inventory** (#6) — enumerate every vault-scoped artifact a lock-screen burn must clear so onboarding-after-burn ≡ onboarding-after-fresh-install byte-for-byte.
- **Non-negotiable implementation guards:** wire the wipe **only** to the lock-screen unlock dispatch, never to the general `Burn` outcome every candidate-check shares (#16 — a self-DoS otherwise); reject any setup passphrase matching an existing slot (#3); `imageLock` + refuse-if-delete-pending (#15); keys-first crash-durable fail-closed arming/wiping + boot-time reconciliation of a half-torn image (#4, #20); slot-0 never biometric-wrapped (#17); verify backup exclusion (#11).
