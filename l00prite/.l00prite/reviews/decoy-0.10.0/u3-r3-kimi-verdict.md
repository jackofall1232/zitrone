**Verdict: P1.**

**1. Severity.** P1, and it isn't close. R-U3-3 is stated as an absolute ("uniform, **never** intermittent"), and this path produces exactly the prohibited artifact: a non-uniform, intermittent failure with a marked frame. The defect *class* — undrained disconnect stranding a mid-gap pairing — is byte-for-byte the class already ruled P1 for teardown. Position B's entire case ("rare," "not lock-correlated," "reconnects immediately," "not adversary-triggerable") is a frequency-and-window argument, which the standing precedent explicitly assigns to *priority*, not *class*. Accepting B would silently re-litigate the precedent on grounds the precedent already excluded. The "non-terminal quiesce is hard and I declined to add it unreviewed" reasoning is a sound *process* decision and zero severity argument — remediation cost has never moved a categorical requirement down a class. P3 ("correctness nit, doc or test gap") is not available: this is a live deniability defect, not a nit.

**2. Split vs. missing — the crux.** Position A is right: the split is the **stronger** signal. A simply-missing cover frame is a single low-grade anomaly — one unpaired frame, plausibly attributable to jitter in isolation. A split pair is a *structured* anomaly: two identical-length frames, milliseconds apart, straddling a TLS teardown-and-immediate-reconnect. That does three things a missing frame doesn't: (a) it lets the observer **pair frames across connection boundaries**, defeating the unlinkability the padding exists to provide; (b) it binds the marked frame to an independently observable infrastructure event (the reconnect), giving the observer a cross-check; (c) the reconnect pattern itself is a fingerprint of a transport change, so the marked frame is now correlated with "user just altered their anonymity transport" — a *more* privacy-significant action than locking the vault, not a less significant one. Dropped cover = one marked frame. Split cover = one marked frame plus a cross-connection linkage plus a trigger classification.

**3. Rarity / user-initiated.** Does not reduce class. The precedent is explicit and Position B concedes it while arguing around it. Rarity and non-triggerability are legitimate inputs to *when* this gets fixed — it can sit behind more frequent-path work in the queue — but not to *what* it is. Note also that the P1 teardown ruling rested on correlation with a *user action*; a transport toggle is a deliberate user action whose network signature (abrupt TLS teardown + immediate re-establishment, possibly changing guard/endpoints) is often inferable by the observer without any triggering capability. The "not adversary-triggerable" point addresses exploitability, and the observer doesn't need to trigger anything — they need to *recognize* it.

**4. The tripwire exclusion.** It does not change the class — the rating stands on the requirement violation alone — but it eliminates the only mitigating consideration and should raise remediation *priority* within P1. A guard that deliberately excludes the known-bad path converts a latent defect into a known, unmonitored violation: no detection net, no regression alarm if the path widens (e.g., auto-reconnect on transport failure reusing the same code), and an undocumented standing exception to an absolute requirement. Minimum bar: either extend the tripwire to this path or record the exclusion as an explicit, reviewed, tracked exception tied to the scheduled quiesce work — not a silent carve-out in the checker.

**Bottom line:** P1 — same defect class as the ruled-P1 teardown case, with a worse signal shape (cross-boundary split), per the precedent that frequency sets priority rather than class. Fix priority may be moderate; the lifecycle-state design work and the tripwire exception should both be tracked as part of the P1 record.
